# 実装から開発資料を復元する

対象の版、読める資料、利用者が欲しい成果物を確認する。指定がなければ現在の版から進め、範囲を出力に添える。開発資料は日本語で書く。顧客の書式がある場合はその項目を優先する。

## 初回の復元

1. 入り口から実際の処理、設定、データ更新、例外時の戻り方まで追う。テストコードは何を確かめようとしているかの根拠に使い、実行結果は別に扱う。画面しか使えないときは、観察した条件と結果を記録する。
2. ソースから分かった現行動作と、業務で必要な振る舞いを別の項目にする。対象を誰が、なぜ、どの条件で承認したかは意思決定の記録を探す。資料が欠けていれば値を空け、確認すべき問いと確認先を添える。実装と社内規程が食い違うときは双方を示す。
3. [工程ごとの成果物](references/deliverables.md)から該当する資料と必須欄を選ぶ。対象外は理由を添える。利害関係者には普段の業務と例外を尋ね、コードに現れない要求も取り上げる。
4. 継続して使う案件では、[台帳の形式と使い方](references/ledger.md)に従い、一項目ずつ根拠の行、対象版、関連項目を記録する。`scripts/ledger.py`で参照を照合してからMarkdownを作る。個別の質問には、該当する根拠と結論を直接答えてよい。

台帳を作る依頼では、最初にこのスキルのディレクトリから `references/ledger.md` を開く。JSONの最上位は `{"schema_version":2,"revision":"対象版","records":[]}`。根拠は同梱の `scripts/ledger.py cite` で取得し、試験結果は元の報告書の試験IDと対象版を照合する。回答する前に、生成したJSONそのものを `scripts/ledger.py check` に渡してエラーを修正する。読み取り専用の作業場所では標準入力 `check - --root 対象フォルダー` を使える。

## 成果物をファイルにする

個別文書や一式の生成依頼では、最初に [案件設定・生成コマンド](references/project.md) を開く。利用者がソフトウェアだけを渡した場合も、対象版の実装・既存資料・試験を読み、作業場所に案件設定と必要な台帳を自分で作る。利用者にJSONの準備を求める必要はない。

顧客の納品指定があれば優先し、指定された文書だけなら `only` を使う。指定がなければ引継ぎの基本7種を起点に、案件で行う受入・運用・移行等を選ぶ。対象かどうかの判断がつかないものは、仮定と確認先を伝える。要件には利用者と受入条件、試験には前提・操作・期待値、結果には同じ版・試験IDの実行記録を記す。期待値と実測値を別々の欄に書く。

運用・移行・設計なども選んだ場合は、判明した手順や制約を台帳の `sections` で該当の節に結ぶ。スキルと同じ場所にある `scripts/documents.py plan` で内訳を確認し、`build` で指定先にMarkdownを生成する。生成後に成果物一覧と依頼された本文を開き、要件から試験への対応、実測と未確認欄を点検する。人の承認や実施の記録が不足する欄には問いを残す。

大規模案件では `inventory` で版と構成を確認し、サービス・業務・共有部品ごとに台帳を分ける。公開API・設定・ジョブ・画面などの入口から必要な実装と試験へ絞り、調査済みの範囲を明示する。共通機能に依存する箇所はモジュール間の番号で結ぶ。各部分を `build --module` で検証してから全体を生成する。未調査の範囲を完了扱いにしない。

## 変更後の確認

以前の台帳を読み、同じ仕様には同じ識別番号を使う。実装変更と、実装が同じまま業務ルールだけ変わった場合の両方を扱う。変更の根拠と承認者が分かる記録を追加し、影響する資料・再実行するテスト・未解決の相違を示す。新しい版での合否にはその版の実行記録を使う。人の回答や以前の結果を旧版に保ち、差分を確認して新版を作る。
