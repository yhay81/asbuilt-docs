# 製品の目的、関係者、構成図と操作画面

初見の読者が最初に開く資料を作る。製品は何をするものか、誰のどの仕事を何のために支えるか、その中で今回どこを復元したかを書く。開発資料を作る目的と、製品を使う目的は別の欄にする。企画時の動機や正式な権限者が不明なら、現行の業務説明の出典と確認先を示す。

## 概要の入力

案件設定に `"overview":"overview.json"` を加える。スキルを使うエージェントが調べて作るファイルである。ファイルの置き場所は案件設定を基準とし、根拠と画像の入力パスは `build --root` を基準とする。添付ファイルを使う場合は同じ入力ルートにコピーする。

| 項目 | 内容 |
|---|---|
| revision、product、purpose、scope | 案件設定と同じ対象版、製品が何か、利用者にとっての目的、今回の範囲。 |
| scope_type | 製品全体なら `product`、製品の一部を扱うなら `subsystem`。後者では software の図に `level: product` と `level: detail` をそれぞれ用意する。 |
| sources、evidence | sources は根拠番号から `{"path":"README.md","start":3,"end":5}` への辞書。選んだ行を付録に収録するので、共有できる該当行だけを使う。既存の引用を固定するには sha256 を指定する。概要と以下の各説明の evidence は根拠番号の配列。 |
| stakeholders | id、name、role、goal、evidence を持つ配列。利用者・入力元・結果の受け手・意思決定者など、実際に関わる人について、何をしたいか、何を入力し何を引き受けるかを書く。組織の人事・契約上の責任まで実装から推定しない。 |
| components | id、name、role、evidence を持つ配列。実行環境、ソフトウェアの主要部品、データの保存先、外部システムに名称を付け、入力・責任・出力を説明する。図に出す人や部品には一覧と同じ id を使う。 |
| views | 下の3種類の図。各要素は kind、title、scope、evidence、edges。edges は `{"from":"client","to":"service","label":"注文番号と数量"}` の配列。孤立したノードは nodes に id を列挙できる。groups に `{"端末":["client"]}` のように配置境界を指定できる。 |
| ui | GUIアプリは `{"kind":"gui","captures":[…]}`。画面を持たないライブラリ等は `{"kind":"none","reason":"…"}`。画面の有無も不明なら unknown と調査範囲を書く。 |

## 三つの図で答える問い

- **infrastructure**　利用端末からどの入口を通り、どの実行環境と永続化先に届くか。配備定義、実際の稼働確認、ローカルの検証環境を区別する。単一端末で完結する製品はその実行境界を描く。
- **software**　利用者の操作を受ける部品、業務の判断をする部品、保存や外部連携を受け持つ部品は何か。呼び出す向きと責任分担を実装で確かめる。
- **data**　代表業務で、何のデータが、誰・どの部品からどこへ渡り、どこで変化・保存され、誰に戻るか。数量、状態、戻り値など実際に受け渡すものを矢印に書く。必要なら順番を付ける。

製品の一部を復元する場合、最初のソフトウェア図で、利用者が知っている業務や主要な機能を使って製品全体を描く。今回の機能がどの業務・共有部品とつながるかが読めるようにする。次の図では今回の機能の内部に入り、画面、判断、保存や外部連携の責任を示す。同じフレームワークが端末とサーバーで動くときは、処理の所在が分かる名前を付ける。役割表には結果の利用者も含め、日常業務で判断する人と製品の正式な受入判断を行う人の根拠をそれぞれ示す。後者が不明なら確認先を記す。

大規模な構成は同じ kind の追加図でサービスごとに詳述できる。根拠が足りない構成は、確認できた範囲を描き、unknown に不足する資料・確認先を記す。接続先が一つも分からない場合も、当該図に調査範囲と確認待ちを示す。

## 画面の採取

対象版を起動し、代表操作の前後を確認して実際のウィンドウ／ブラウザーをPNGまたはJPEGで撮る。提供された同じ版の撮影原本も使える。合成業務データを優先し、依頼者側・利用者側の違いや、操作できる／できない状態が判断に関わる箇所を選ぶ。認証情報などが映る画面は状態を変えて撮り直す。CLIやAPIに架空の画面を描かない。必要な環境を用意できない場合は `kind: gui`、空の captures、reason に理由・必要な手段と確認先を入れ、採取待ちと分かる形で渡す。設計モックや生成画像で実際の画面を代用しない。

各 capture に file、sha256（撮影原本のバイト列）、revision、title、actor（関係者id）、action、state、captured_at、environment を記入する。environment には端末／ブラウザー、画面寸法、合成入力や模擬接続の有無を記す。画像から見えた状態と、サーバーの動作を証明する試験原票は、それぞれの出典で扱う。

`documents.py build` が三つの図をSVGとして描画し、画面原本を検証して納品先にコピーする。Graphviz が使える環境ではノードと境界を自動配置し、その他の環境では同じ有向関係を行別に描く。撮影原本のSHA-256が納品先にも残り、`check-delivery` で画像を再照合できる。完成後に図と画像を実際に開き、文字・矢印・画面の状態とキャプションが読めるか確認する。
